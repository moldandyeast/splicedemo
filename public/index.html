Two-slot procedural console · CART-1 protocol

SPLICESP-2

A console with two cartridge slots, after an idea by flomerboy. A cartridge is not a game. It holds story beats and rules written in a small YAML language. Put two in and the console weaves them into one new game, joining every beat with but or therefore, never "and then". Swap the slots and you get a different game.

Insert two cartridges, switch the power on, press Start.

          01 · ConceptTwo slots, one game
          
        
          Every cartridge describes a small slice of a game: a world, a cast, a look, and a short list of story beats. Each beat changes the rules of play. Insert one cart and it plays on its own. Insert two and the console splices them: slot I supplies the world and the spine of the story, slot II supplies trouble. The pair is woven into a single sequence of beats, and every beat becomes a level whose rules are solved on the spot.
          
        
          
          
          Cart Ilunar-post.yaml
          +
          Cart IIsnake-pit.yaml
          →

          →
          Planbeats + rule states
          →
          Enginelevels solved live
          
        
          
        
          The same pair always produces the same game, because the seed is a hash of the two cart ids in slot order. Swap the carts and the seed, the genre, the art and the story order all change.
          
      
          
      
          
        
          02 · ResearchWhat we kept from Tinker Studio
          
        
          Tinker Studio is our procedural animation engine: a robot whose every pose is solved from constraints, IK and springs, driven by a timeline of clips. Splice reuses its principles, moved from animation to game design.
          
        
          
          
          Tinker StudioSplice
          
          
            
          Clips, not keyframesBeats, not levels. A beat only says which rules apply. The engine builds the level from those rules, the way the rig blends between clips through its springs.
          
            
          Seeded random generatorThe seed is FNV-1a of idI|idII, plus the beat index. Same carts, same game. A retry rebuilds the identical level.
          
            
          Fixed timestep, 240 HzFixed timestep at 60 Hz with an accumulator, so physics and spawns replay the same on every machine.
          
            
          Constraints instead of animationConstraints instead of hand-made maps. Platform ledges are anchored within jump range of the layer below. Top-down rooms only place pillars on even cells, so every room stays connected.
          
            
          Behaviours as modesVerbs, hazards and twists are registered modules with the same small interface, so carts can name them and anyone can add more through the API.
          
            
          Technical-drawing lookOne bit per pixel, four art treatments (solid, outline, dither, stripe) and three palettes. The hardware is drawn as line art with hatched shadows.
          
                    
        
          
      
          
      
          
        
          03 · LanguageThe CART-1 schema
          
        
          A cartridge is one YAML document. Five sections, all short.
          

          cart: 1                 # protocol version, required
id: lunar-post          # 2–24 chars, lowercase, digits, dashes
title: Lunar Post       # up to 18 characters
role: spine             # spine | trouble | either  (slot hint)
style:
  art: outline          # solid | outline | dither | stripe
  palette: paper        # paper | night | lcd
world:                  # only read from slot I
  verb: platform        # platform | topdown | shmup | runner
  hero: astronaut       # any sprite
cast:
  item: letter          # what you collect
  foe: blob             # what hunts you (slot II's foe wins)
beats:                  # 1–6 beats, played in order
  - setup: the last mail carrier on the moon has six letters to deliver
    set: { goal: collect, count: 6, hazards: [walker] }
  - but: the low gravity makes every jump drift
    add: { twists: [lowgrav] }
  - therefore: you climb toward the relay tower to send them home
    set: { goal: reach }
    add: { density: 1 }
          
        
          Beat operations
          
        
          
          
          OpWorks onEffect
          
          
            
          setany rule keyReplaces the value. Lists are replaced whole.
          
            
          addhazards, twists, count, time, distance, timer, densityLists gain new names. Numbers are summed, so add: { density: 1 } raises pressure.
          
            
          drophazard or twist namesRemoves them. drop: [dark] turns the lights back on.
          
                    
        
          
        
          Rule keys are verb hero item foe goal count time distance timer density art palette hazards twists. State carries forward from beat to beat, so a beat only states what changes.
          
      
          
      
          
        
          04 · StoryBut and therefore
          
        
          Trey Parker and Matt Stone's rule for South Park: if the beats of your story are joined by "and then", it is boring. Join them with "but" (a complication) or "therefore" (a consequence) and the story drives itself. CART-1 builds this into the grammar.
          
        
            
          
          1. A beat's story line is keyed by exactly one connector: setup, but or therefore.
            2. 
          
          2. and and then are rejected by the parser. They are not connectors.
            3. 
          
          3. A beat that changes no rule is reported as an "and then", because nothing in play changes. If woven beats still land on the same rules, the weaver raises density by one so every beat is felt.
            4. 
          
          4. When carts are woven, connectors strictly alternate: SETUP, BUT, THEREFORE, BUT… The weaver rewrites a beat's connector when its position demands it, and logs the rewrite.
            5. 
          
          5. Write story lines as clauses that read after either word: "the snakes wake up and start to hunt".
            6. 
        
          
      
          
      
          
        
          05 · CompositionThe weave algorithm
          

          weave(I, II):
  seed   = fnv1a(I.id + "|" + II.id)
  state  = defaults ← I.world ← I.style ← I.cast
  state.art  ← II.style.art        # slot II paints the game
  state.foe  ← II.cast.foe         # slot II brings the trouble
  queue  = [I.beat1]               # the setup always comes from slot I
  then alternate II, I, II, I…     # leftovers from the longer cart follow
  trim to 8 beats
  for beat n in queue:
    conn  = n == 0 ? SETUP : (n odd ? BUT : THEREFORE)
    state = apply(state, beat.set, beat.add, beat.drop)
            # slot II may not change verb or hero: "world is owned by slot I"
    last beat: density + 1  (the finale)
  return plan { title, seed, beats[ {conn, text, src, state, diff} ], trace }
          
        
          Because slot II beats land on odd positions they usually read as BUT, and slot I beats as THEREFORE: the second cart complicates, the first cart responds. With one cart, its own beats alternate in order.
          
      
          
      
          
        
          06 · InteropChannels and merge policy
          
        
          Every key belongs to a channel, and each channel has one owner. This is what lets any cart combine with any other without conflicts.
          
        
          
          
          ChannelOwnerPolicy
          
          
            
          world.verb, world.heroSlot ILocked. Slot II writes are ignored and logged.
          
            
          style.paletteSlot IFalls back to slot II when slot I has none.
          
            
          style.artSlot IISlot II paints over slot I.
          
            
          cast.itemSlot IFalls back to slot II.
          
            
          cast.foeSlot IIOverrides slot I.
          
            
          beatsBothInterleaved, connectors re-assigned by position.
          
            
          goal, counts, hazards, twistsWhoever's beat is playingset replaces, add stacks, drop removes. Carries forward.
          
                    
        
          
      
          
      
          
        
          07 · ReferenceVocabulary
          
        
          Generated from the engine's live registry. Names you register through the API appear here and become valid CART-1 at once.
          
        
          
      
          
      
          
        
          08 · CraftAuthoring rules
          
        
            
          
          1. Three or four beats per cart. Six is the limit; a woven game is capped at eight.
            2. 
          
          2. Give every beat one clear rule change the player can feel: a new hazard, a twist, a new goal.
            3. 
          
          3. Spine carts should set world and a goal in their setup. Trouble carts can leave the world out and only add pressure.
            4. 
          
          4. Keep titles to 18 characters and story lines under 90 so they fit the label and the story card.
            5. 
          
          5. Test a cart in both slots. A good cart is fun as the world and as the trouble.
            6.

          HardwareConsole
          

          const c = Splice.console
c.insert(0, 'star-siege')       // slot 0 is slot I, slot 1 is slot II
c.insert(1, 'blackout')
c.power(true)                   // boots, weaves, shows the title screen
c.press('start')                // simulate a controller tap: up down left right a start select
c.swap(); c.reset()
const off = c.on('beat', b => console.log(b.conn, b.text))
// events: power, insert, eject, weave, beat, clear, death, end
c.status                        // { power, mode, beat, deaths, slots }
          
        
          Changing a cartridge while the power is on behaves like real hardware: the picture breaks and you press Reset.

          ExtendRegister modules
          

          // a new sprite, usable as hero, item or foe
Splice.register.sprite('duck', ['........','..##....','.#.##...','.####...','..######','..#####.','...###..','........'])

// a new twist: ice makes the hero slide
Splice.register.twist('ice', {
  label: 'Ice', desc: 'Floors are slippery.',
  tick(L) { if (L.p.vx !== undefined) L.p.x += (L.p.lastVx || 0) * 0.6; L.p.lastVx = L.p.vx; }
})

// a new palette
Splice.register.palette('amber', { label:'Amber', desc:'Amber phosphor.', c:['#120B00', '#FFB000'] })
          
        
          After registering, the names validate in the IDE, appear in the vocabulary, and work in any beat: add: { twists: [ice] }.
          
      
          
      
          
        
          InterfaceModule interface
          
        
          
          
          KindShape
          
          
            
          verb{ label, desc, scrolling, stomp, build(L), update(L, input), solid(L, cx, cy), spots(L) }
          
            
          hazard{ label, desc, killable, init(L), tick(L), update(L, e) }
          
            
          twist{ label, desc, build?(L), tick?(L) }
          
            
          art{ label, desc, fn(x, y, edge) → bool } decides which pixels of a sprite or tile are lit
          
            
          palette{ label, desc, c: [paper, ink] }
          
            
          spriteeight strings of eight characters, # lit and . dark
          
                    
        
          
        
          L is the live level: L.p the player, L.ents entities, L.s the resolved rule state, L.rng() the seeded generator, L.t frames elapsed. input is { x, y, a, aP, upP, start }.
